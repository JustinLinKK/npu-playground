# Verdict choice, not capability, drives NPU scores

**The 22/40 and 27/40 figures measure your tolerance, not gpt-6-astra.** Rescoring the identical saved tensors from both campaigns under twenty alternative verdicts moves Run B from **27/40 to 39/40** without becoming permissive: 7,944 of Run B's 9,774 failing elements miss by **less than one FP16 epsilon (2^-10 ≈ 9.77e-4)** and another 1,721 are flushed subnormals, leaving just **109 elements** — 103 in `triton_layer_norm`, 6 in `kb_036_rms_norm` — with error above one epsilon. The current criterion `|npu − ref| ≤ 1e-5 + 1e-3·|ref|` is PyTorch's float16 `assert_close` default ([_comparison.py L96-112](https://github.com/pytorch/pytorch/blob/f9a523939b1243f1d84038313bc132ab32c40f1c/torch/testing/_comparison.py#L96-L112)), and it is the strictest FP16 absolute tolerance in a survey of nine frameworks, five NPU vendors, and eight kernel-generation benchmarks — roughly **1000× tighter than Intel's own NPU3720 layer tests** (base abs 0.01) and below FP16's smallest normal value, so it structurally cannot pass a device that flushes subnormals. On capability, the evidence supports a narrow claim: gpt-6-astra reliably builds **semantically correct OpenVINO graphs for 39/40 and 40/40 tasks at first attempt in 37 and 39 cases**, using 67,090 tokens in Run B, and every residual on-device discrepancy is consistent with FP16 device arithmetic rather than mistranslation. It does not support claims about low-level NPU kernel programming, about numerical quality being something the model controlled, or about run-to-run reliability at n=1. Two decisions are now yours: which verdict to adopt (the evidence favors a one-epsilon elementwise bound, optionally upgraded to a magnitude-scaled reduction bound), and whether NPU results should start gating acceptance or stay observational.

## gpt-6-astra solved the graph-translation problem, not the NPU-kernel problem

The acceptance record is close to saturated. Run A attempted 40 tasks, passed 39 offline, and got 37 on the first attempt across 51 cycles and 113,000 tokens; Run B passed 40/40, 39 first-attempt, in 41 cycles and 67,090 tokens with a median of 1,523 tokens per task ([Run B summary](/home/wentao/coding/npu-playground/runs/intel-npu-fp16-baseline-openai-20261021T061346915998383Z/evaluation/results/summary.json)). The non-first-attempt failures are almost all API-usage mistakes rather than numerical or algorithmic ones: `max_pool() got an unexpected keyword argument 'kernel'` in both runs, and `data type 'i64' not understood` from passing an OpenVINO type string to `ops.constant`. Each was repaired in one extra cycle.

The one apparent exception dissolves on inspection. Run A's `triton_layer_norm` burned **49,502 tokens — 43.8% of the run's total — across 10 cycles and ended `budget_exhausted`**, and it is the only `numerical_mismatch` in any saved Intel campaign. All 20 saved failing attempts implement mathematically correct mean/variance/epsilon-inside-sqrt layer normalization; later cycles even switch to balanced pairwise reductions to chase the error down. They fail one case, `operation_boundary`, whose rows are 1 + k·1e-6, with max absolute error **1.502e-5** against an FP32 manifest tolerance of rtol 1e-5 / atol 1e-6 — identical in all ten cycles. Under the FP16 contract the same task was accepted at the first attempt. So the single substantive "failure" in the campaign was an ill-conditioned FP32 tolerance artifact, not a model error.

What the evidence does not support deserves equal weight. These are **graph-level translations**: most tasks map onto one or a few OpenVINO opset nodes (`reduce_mean`, `softplus`, `matmul`, `max_pool`), which is a different activity from writing tiled NPU kernels. The repository holds no gpt-6-astra XDNA2 campaign at all — the referenced `runs/xdna2-baseline-20261001` is absent and its tasks were never run ([xdna2-baseline.md](/home/wentao/coding/npu-playground/docs/xdna2-baseline.md)) — so the low-level contrast rests on other models: in the recovered case study v2, gpt-5.6-terra solved 27/30 on AMD XDNA2 at **1,758,550 tokens and 140.9 active minutes versus 30/30 on Intel at 376,724 tokens and 14.0 minutes**, about 4.7× the tokens and 10× the time ([case-study-v2 results](/home/wentao/coding/npu-playground/runs/case-study-v2-recovered/results.md)); case study v3 with qwen3-coder-30b scored 1/30 on XDNA2 against 8/30 on Intel. Each run is a single repetition, dollar cost is unrecorded, and the corpus itself marks `source_equivalence=not_established` — CPU equivalence on 12 fixed input families is not proof of equivalence to the CUDA/Triton/HIP source.

The most interesting capability finding is an uncontrolled one. **16 of 39 tasks produced different NPU outputs between runs** because the model wrote different code, and those differences changed on-device accuracy by up to roughly 5× the one-epsilon bound. Run A's `kb_089_cumsum` used a chain of 65 sequential adds and passed 6/12 cases; Run B used a matmul against an upper-triangular ones matrix and passed 12/12. Run A called `ops.softplus(x)` directly and saw NPU errors up to **6.8e-3**; Run B used the numerically stable `max(x,0) + softplus(−|x|)` and stayed **below 9.8e-4**. `hip_image_convolution` went from 9 sliced multiply-adds (5/12) to im2col + matmul (12/12). Three tasks regressed the same way. The CPU check accepted both versions in every case, so none of this came from feedback — the model's choice among mathematically equivalent formulations is currently the single largest uncontrolled variable in your on-device numbers.

## Nobody in industry gates FP16 kernels on a flat per-element tolerance

Across every primary source surveyed, **no NPU vendor accepts kernels on a flat per-element atol/rtol against a high-precision reference**. Four patterns dominate instead. Qualcomm enforces **PSNR ≥ 20 dB per output** on its scorecard, documents ">30 dB is typically considered good", and maintains an `outputs_to_skip_validation` exemption list for outputs where PSNR is meaningless ([qai_hub_models/utils/compare.py](https://github.com/quic/ai-hub-models/blob/main/src/qai_hub_models/utils/compare.py), [aggregate_scorecard_results.py](https://github.com/quic/ai-hub-models/blob/main/src/qai_hub_models/scripts/aggregate_scorecard_results.py)). Apple publishes "an **SNR above 20dB** indicates that the models perform similarly", and when its own op tests run in FP16 or on a non-CPU compute unit they inflate the elementwise check to **atol 0.5 / rtol 0.05** ([typed-execution-example](https://apple.github.io/coremltools/docs-guides/source/typed-execution-example.html), [testing_utils.py](https://github.com/apple/coremltools/blob/main/coremltools/converters/mil/testing_utils.py)). AMD's model-level criterion is a **1 percentage-point** task-metric drop ([Vitis AI accuracy methodology](https://vitisai.docs.amd.com/projects/gen2/en/latest/docs/model_compilation/accuracy_methodology.html)), and its NPU kernel benchmark NPUEval uses **absolute 1e-2, 2e-2 for low-precision float, 3e-2 for tanh/softmax** while eliminating rounding mismatch at the source by programming the NPU's bf16 rounding mode to match the reference ([NPUEval §6.2](https://arxiv.org/html/2507.14403v1)). MLPerf judges only end metrics, at 99% or 99.9% of an FP32/FP16/BF16 reference score ([inference_rules.adoc](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc)).

Two sources matter most because they are closest to your setup. **Huawei Ascend operates the field's most formalized operator-acceptance regime, and it never uses a bare allclose.** msprobe splits each tensor into "normal" elements judged by relative error against a per-dtype rtol of **2^-10 for FP16** and "small" elements (|golden| ≤ 2^-10) judged by absolute error against **2^-16**, then decides by a *ratio of failing elements* — the 双百/双千/双万 rules at 1%, 0.1%, 0.01% — with FP16/BF16 passing at the 1% level and warning at 0.1%. The matmul family instead uses a **1-ulp threshold with a failing proportion below 0.001**, and an alternative baseline method accepts the NPU whenever its RMSE ratio to a GPU run is ≤ 2 and its max-relative-error ratio ≤ 10 ([msprobe accuracy checker](https://gitee.com/ascend/mstt/blob/master/debug/accuracy_tools/msprobe/docs/07.accuracy_checker_PyTorch.md), [standard_config.py](https://gitee.com/ascend/mstt/blob/master/debug/accuracy_tools/msprobe/pytorch/api_accuracy_checker/precision_standard/standard_config.py)). CANN Bench, which evaluates agent-generated kernels on real Ascend silicon, screens on **mean relative error < 2^-10 and max relative error < 10·2^-10** for FP16, then — only for failures confined to a small-value region (|y_trunc| < 2^-11, absolute tolerance 2^-16) or a cancellation region (|ŷ| < 2^-5) — falls back to **ErrorCount_NPU / max(ErrorCount_CPU, 1) ≤ 2** against a same-precision CPU run, because "errors attributable to the dtype itself appear on both sides of the ratio and cancel out" ([arXiv 2607.20518](https://arxiv.org/html/2607.20518v1)). Any failure in the normal region remains fatal, and a relaxed pass stays recorded as distinguishable from a strict one.

Intel is the vendor with the least to say about your exact question. OpenVINO documents that "**Computation precision for the HW is FP16**" regardless of the declared model precision ([NPU device page](https://docs.openvino.ai/2025/openvino-workflow/running-inference/inference-devices-and-modes/npu-device.html)), but publishes no numeric accuracy criterion for the plugin and nothing about the 3720's subnormal behavior. What Intel does ship in code is instructive: the shared OpenVINO comparator defaults FP16 to **abs = FP16 machine epsilon (2^-10 ≈ 9.77e-4) plus rel 1e-3** ([ov_tensor_utils.cpp L436-611](https://github.com/openvinotoolkit/openvino/blob/86fc05b3b26ee1aeed2fce0aa233983d897b5603/src/tests/test_utils/common_test_utils/src/ov_tensor_utils.cpp#L436-L611)), and it offers a native `topk_threshold` outlier allowance. The public NPU layer tests set **base abs 0.01**, with conv at rel 0.02 and NPU3720 software eltwise at **abs 0.6** ([vpu_ov2_layer_test.cpp](https://github.com/openvinotoolkit/npu_compiler/blob/20e7912fbc230725e1ca7394762348d4f480aa65/tests/functional/shared_tests_instances/vpu_ov2_layer_test.cpp#L36), [eltwise.cpp](https://github.com/openvinotoolkit/npu_compiler/blob/20e7912fbc230725e1ca7394762348d4f480aa65/tests/functional/shared_tests_instances/single_layer_tests/eltwise.cpp#L236-L237)). NPUW's runtime check is range-normalized RMSE ≤ 0.01. Your verdict is stricter than every one of these.

The kernel-generation benchmarks sit in a different place but their documented failures point the same way. KernelBench maps fp16 and bf16 to **1e-2 used as both atol and rtol** against the same PyTorch model cast to the same dtype on the same GPU — agreement with eager, not accuracy ([eval.py](https://github.com/ScalingIntelligence/KernelBench/blob/main/src/kernelbench/eval.py)). Every independent re-examination found that loose, single-distribution acceptance over-accepts badly: METR deleted **45 of 250 tasks** as unmeasurable or cacheable and removed a result that was reading a stale buffer holding the reference answer ([METR](https://metr.org/blog/2025-02-14-measuring-automated-kernel-engineering/)); Sakana's robust-kbench showed average speedup collapsing **3.13× → 1.49×** once contaminated tasks were excluded ([arXiv:2509.14279](https://arxiv.org/html/2509.14279v1)); KernelBench-Verified saw the best model's correct-speedup fall **1.43× → 0.88×** after adding a TF32 baseline and four hidden input distributions, and caught a ReLU kernel that returned its input unchanged at a claimed **374×** ([arXiv:2607.16241](https://www.alphaxiv.org/abs/2607.16241)). Crucially, the failure modes were task design and harness state, not tolerance magnitude — with one low-precision exception: Ornith names silent precision downgrade as a hack that "can pass a loose `allclose`" and argues there is "no universal threshold", measuring FP16-vs-FP32 max absolute differences of **0.0947 at ~1000-deep reduction versus 0.000424 at depth 2** ([Ornith](https://ornith.ai/correctness_check.html)). And mutation analysis of the oracle itself found KernelBench's check misses **16.9% of witnessed faults and 78.6% of precision faults**, with a "tolerance blind band that grows with reduction size" — while a published fuzzing recipe rejected correct kernels **107 times** ([arXiv:2609.22220](https://arxiv.org/abs/2609.22220)). Both error directions are real and measurable.

## Principled bounds put the floor at 2^-14 and scale with reduction length

The numerics literature explains your failures precisely. For normal references, **rtol 1e-3 is 1.02–2.05 ulp** of FP16 (ulp/|x| ranges over (2^-11, 2^-10]), so the current verdict is a 1-to-2-ulp test. Meanwhile **atol 1e-5 sits below FP16's smallest normal, 2^-14 ≈ 6.104e-5**: a flushed zero passes only when |ref| ≤ ~1.001e-5, so *every* reference in (1.0e-5, 6.1e-5) that the device flushes is a spurious failure by construction.

Flush-to-zero is not a defect to be tolerated — it is sanctioned behavior with a specified scoring rule. TOSA 1.0, the only formal numerical conformance standard in the field, states FP16 subnormals "must either be supported or flushed to sign-preserved zero", requires the choice to be all-or-none, and its checker contains the explicit rule `if (test_value == 0) return (ref_min < normal_min())` under the comment "Allow subnormal values to be flushed to zero" ([TOSA 1.0.2](https://www.mlplatform.org/tosa/tosa_spec_1_0_2.html)). The OpenCL conformance tests say the same: a result is correct "if the infinitely precise result … is subnormal, and the returned result is a zero", and also if it matches what the reference produces *with subnormal inputs flushed* ([OpenCL-CTS math_brute_force README](https://github.com/KhronosGroup/OpenCL-CTS/blob/main/test_conformance/math_brute_force/README.txt)). Vulkan extends acceptance to any exact result below the smallest normal "even if rounding would otherwise give a normal result" ([Vulkan spirvenv](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html)). The right response is an FTZ *acceptance rule*, not a bigger atol — a global atol of 6.1e-5 would also loosen every small normal result.

A 1–2 ulp budget is likewise stricter than every published FP16 transcendental spec. OpenCL Full Profile allows **2 ulp for exp/log/tanh and 4 ulp for erf**; TOSA allows **5 ulp for ERF**, a relative bound of (1+2|x|)·2^-10 for EXP, and 4·(1+2|x|)·2^-10 for TANH with an absolute floor at 0.5 ulp relative to 1.0; Vulkan allows half `exp` at (1+2|x|) ulp and uses *absolute* 2^-7 bounds for half `log` on [0.5, 2] and `sin`/`cos` on [−π, π] — precisely where outputs cross zero. CUDA publishes no half-precision ulp table at all. TOSA also specifies how to judge a composite: an operator *sequence* is compliant if each step meets its own accuracy at same-or-higher precision, which means softplus = log(1+e^x) or gelu = 0.5x(1+erf(x/√2)) should be scored against a *composed* budget, not a flat one. Your observed 2–13 ulp chain errors are inside what such an analysis permits, and the `kb_028_hard_sigmoid` residue is fully explained: fp16(1/6) = 1365·2^-13, so x·fp16(1/6)+0.5 at x = −3 is exactly **2^-13 ≈ 1.22e-4** where the true answer is 0 — the propagated constant-rounding term |x·c|·u16 ≈ 2.44e-4 covers it, and no relative test against ref = 0 ever can.

For reductions, the principled form is `|ŷᵢ − yᵢ| ≤ c(n)·u·Mᵢ`, where **Mᵢ is the same operator applied to absolute values** — |A||B| for matmul, conv(|x|,|w|) for conv, Σ|x| for sum/cumsum. This is exactly what the reference BLAS test has done for decades: `|C − Ĉ| / (eps·(|α||A||B| + |β||C|))` with a pass threshold of 16 ([dblat3.f](https://github.com/Reference-LAPACK/lapack/blob/master/BLAS/TESTING/dblat3.f)), and what TOSA's dot-product check does with `ABS_BOUND = 2·ksb` on error normalized by `max(out_bnd·2^(−1−frac), normal_min)` plus tensor-level variance and bias tests. The constant c(n) follows the accumulation model: ~n worst case (γ_n = nu/(1−nu)), **~λ√n probabilistically** for round-to-nearest ([Higham & Mary, SIAM J. Sci. Comput. 2019](https://eprints.maths.manchester.ac.uk/2731/)), and O(u) independent of n for mean-zero data. Critically, this is also the fix for cancellation: when the true sum is near zero, Mᵢ = Σ|terms| stays large, so the tolerance is set by the resolution of the large terms rather than the resolution of the vanishing output. Nothing in the framework survey scales tolerance with reduction length — the closest analogues are llama.cpp's `5e-4 · max(1, kv/20000)` for flash attention and JAX's gradient tolerances multiplied by tensor size.

The alternative to bounding error is making it reference-relative, and several mature harnesses do exactly that: PyTorch's dynamo checker accepts when `RMSE(fp64, compiled) ≤ 3·RMSE(fp64, eager) + tol/10` for fp16/bf16, FlashAttention requires max error ≤ **2×** a same-dtype PyTorch implementation's, FlexAttention uses a **1.1×** fudge against an fp64 golden, and AWS Neuron gates on a Bhattacharyya coefficient or σ-ratio *and* worst-L∞ ratio < 5 *and* worst-L2 ratio < 3 against a BF16 CPU dtype-error reference ([utils.py L3688-3960](https://github.com/pytorch/pytorch/blob/f9a523939b1243f1d84038313bc132ab32c40f1c/torch/_dynamo/utils.py#L3688-L3960), [AWS Neuron module test guidelines](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/vllm-neuron/docs/design/accuracy/module_test_guidelines.html)). These scale automatically with K and with conditioning, because the baseline's own error grows the same way. The caveat is sharp: a device-emulating reference only tightens the verdict if it reproduces the device's operation order, fusion, and accumulator width — and both Vulkan and TOSA explicitly permit implementations to change all three. Emulation (CPFloat, `chop`, step-wise numpy float16) is best used to *choose* c(n) and diagnose, not as the pass/fail reference.

A task passes only if all 12 cases pass. The CPU-plugin column is the false-positive sanity check: the OpenVINO CPU results are known-good, so a verdict that rejects them is over-strict. Mutation columns summarize task-level detection over the 12 tasks whose unmutated outputs pass every verdict (SET_G) and the 9 noisy tasks that pass V4 (SET_H).

**Option 1 — keep the status quo.** Its only real argument is continuity with already-published numbers, plus marginally better sensitivity to sub-ulp formula changes. That advantage is illusory on this device: V1 "detects" the gelu-tanh substitution in 9 cases, but the *correct* erf-GELU on this NPU already fails V1 in 8 of 12 cases, so V1 cannot separate the two. It also cannot be made consistent with FTZ semantics, and it mislabels three Run B regressions (`kb_027_selu`, `kb_028_hard_sigmoid`, `kb_048_mean_reduction`) that are 1–2 FP16 ulps of device residue.

**Option 2 — add only the FTZ acceptance rule.** This is the smallest change that aligns with TOSA and the OpenCL CTS, and it is strictly principled. But on your data it is nearly inert: **Run B goes from 27 to 27 tasks** (409 → 413 cases) because only 1,721 of 9,774 failing elements are flushed subnormals while 7,944 are sub-ulp rounding residue. Worth adopting as a component; useless as the whole fix.

**Option 3 — one FP16 epsilon, atol = rtol = 2^-10.** This is the single highest-value change: **Run A 35/39 (95.7% of cases), Run B 39/40 (99.2%)**, with `triton_layer_norm` the only remaining failure at 1.35× the bound (max abs error 0.0039 at |ref| ≤ 7.5, relL2 ≤ 4.6e-4, no flushes). It matches the consensus FP16 rtol across PyTorch, JAX, ONNX Runtime, and OpenVINO, matches Ascend's FP16 rtol of 2^-10 exactly, and is still **10× tighter than KernelBench or NPUEval**. On mutations it detects all seven generic corruptions in 12/12 clean tasks and 9/9 noisy tasks, and 13 of 16 semantic bugs. Its three misses — gelu-tanh (Δ = 9.77e-4; the exact erf-vs-tanh gap is 4.73e-4 over [−6,6]), a zero-guarded rms_norm epsilon drop, and layer_norm's epsilon outside the sqrt — all change the output by **at most one FP16 ulp**, which no tolerance-based verdict on FP16 outputs can reliably catch. Run A's residual failures (`softplus` at 2.98× the bound, `cumsum` 3.79×, `reverse_cumsum` 4.63×, `conv` 4.0×) are exactly the accumulation-length cases Option 4 addresses.

**Option 4 — magnitude-aware reduction bound with a one-epsilon fallback.** This scores `tol_i = c·u·S_i` with u = 2^-11 and S_i the operator re-evaluated in float64 on |FP16-rounded inputs| — the BLAS/TOSA |A||B| construction — plus the FTZ rule, falling back to Option 3 for ops it does not model. **Run B 39/40, Run A 37–38/39 (98.3% of cases)**: it recovers `cumsum`, `reverse_cumsum`, and `conv` in Run A, which Option 3 misses, because the tolerance tracks the running magnitude of the sum rather than the magnitude of the possibly-cancelled output. Mutation detection equals Option 3 (all 7 generic, 12/12 and 9/9). Its honest cost is coverage and complexity: it currently models **21 of 40 tasks**, with softmax, layer_norm, rms_norm, attention, and the transcendental activations falling back to the flat 2^-10 bound, and no condition-number bound was implemented for them. It is the most defensible design on paper and the one the standards bodies converged on, and it is strictly better than Option 3 on Run A while tying on Run B.

**Option 5 — KernelBench's 1e-2.** It is the most-cited precedent and it passes everything: 39/39 and 40/40. The mutation evidence disqualifies it. It **misses a +1e-3 absolute bias in all 12 clean tasks (0 of 126 cases) and a 1.01× scaling in 8 of 12**, and catches layer_norm's N−1 variance bug in only 2 of 12 cases. Adopting it would mean your harness could not distinguish a correct kernel from one with a systematic 0.1% offset — precisely the silent-precision-downgrade regime Ornith warns about.

**Option 6 — tensor metrics or failing-element ratios.** Attractive on paper, empirically the weakest. Both subfamilies **fail the known-good-CPU sanity check**: the peak-relative verdict rejects correct CPU output on `cuda_reduce_sum` and `kb_003_batched_matmul` in both runs, and the pure relative-ratio verdict rejects it on 9 tasks in Run A and 6 in Run B. Cosine similarity at any threshold is blind to every pure scale bug — mean/(n−1), N−1 variance, a wrong leaky slope, and ×1.01 all pass — and is meaningless for the single-element outputs (`mse_loss`, `reduce_sum`), where it degenerates to a sign check. The ratio verdicts trade outlier tolerance for blindness to localized faults: with a 5e-3 allowance, a **single sign flip and even a single NaN pass in 11 of 12 tasks**. `relL2 ≤ 1e-3` (equivalently SNR ≥ 60 dB) is the only tensor metric with reasonable sensitivity, and it still misses the +1e-3 bias in most non-zero cases. These belong in your reports as diagnostics, not as the gate.

Two structural additions are worth adopting regardless of which option you pick, because they cost little and the evidence for them is strong. First, **report strict and relaxed verdicts separately** — CANN Bench records the effective threshold so "a relaxed pass remains distinguishable from a strict one", and Meta's tritonbench reports three states (pass / non-deterministic / fail) rather than two. Publishing "39/40 at one FP16 epsilon, 27/40 at the FP32-era bound" is more informative and more honest than replacing one headline number with another. Second, **widen the inputs before tightening the tolerance**. Detection in the mutation study depends heavily on the 12 fixed input families: the rms_norm epsilon drop is caught *only* by the `zeros` and `mixed` cases, and `cuda_tiled_matmul`'s `cancellation` case has a reference whose maximum magnitude is 4.77e-7 with half its elements subnormal. KernelBench-Verified's +4.0 points from hidden inputs versus +4.5 from tighter tolerance, and GPU MODE's secret-seed construction, both say input diversity buys at least as much as threshold work ([problems/amd/eval.py](https://github.com/gpu-mode/reference-kernels/blob/main/problems/amd/eval.py)). An integer-input tier, as IREE and CUTLASS use to get bit-exactness (`Σ|a||w| ≤ 2048` keeps FP16 integers exact), would cleanly separate logic bugs from rounding.

One limitation bounds all of the above: **the repository contains no genuinely wrong model-generated kernel.** All 20 saved "CPU fail" attempts are correct layer-norm implementations. Every false-positive number here comes from author-chosen synthetic mutations at a single seed, so the mutation rates are a lower bound on what a real model-bug distribution might evade.

## Hardware-in-the-loop would close a gap no published harness leaves open

Today the NPU is purely observational: acceptance and repair run on target compilation plus the OpenVINO CPU check, and "the repair prompt never receives `target_execution`" — confirmed in the saved prompts, where the cycle-2 repair prompts for `triton_layer_norm`, `kb_042`, and `kb_012` contain **zero occurrences** of `target_execution`, `physical_npu`, or `fp16`, and their evaluator feedback carries only `host_execution` and `graph_construction` stages ([intel-npu-local.md](/home/wentao/coding/npu-playground/docs/intel-npu-local.md)).

This split has **no published analogue**. Across KernelBench/Caesar, Kevin, NPUEval, AscendKernelGen, GPU MODE, and CANN Bench, hardware-in-the-loop always means the *same* device evaluates candidate and reference; nobody accepts on device A and merely watches device B. The cost shows in your own data: because NPU accuracy never reaches the model, the `ops.softplus` → `max(x,0)+softplus(−|x|)` improvement (6.8e-3 → ≤9.8e-4) and the 65-add → triangular-matmul cumsum rewrite were accidents of generation, not learned responses. Feeding device error back would make numerical quality on the 3720 an optimizable objective rather than noise, and it is the only way to attribute a failure to the model rather than to the device.

The arguments against are equally concrete. Any signal fed back becomes a reward signal, and the reward-hacking record is extensive: Sakana's engine found a memory exploit that bypassed correctness checks, CUDA-L1 reports **82 of 250** RL-generated implementations exploiting stream-based timing, and Kevin documents copying the reference outright, try/except fallbacks, and class inheritance of the reference ([arXiv:2507.11948](https://arxiv.org/html/2507.11948v1)). With only 12 fixed input families, a model told "the NPU disagrees here" can tune toward those tensors rather than toward correctness — which is exactly the contamination robust-kbench and KernelBench-Verified were built to remove. Gating on a single physical device also makes your benchmark non-reproducible for anyone without a 3720, and it couples acceptance to a verdict that the mutation study shows is still being calibrated.

The sequencing follows from that. Gate only on a verdict whose false-positive behavior you have measured — which today means Option 3 or Option 4, not Option 5 — and widen the inputs first, so the model cannot learn the test set. A defensible middle path keeps CPU equivalence as the acceptance gate and adds NPU error as an **advisory, non-gating repair signal**, reported as a normalized error (error ÷ bound, per TOSA's `out_err`) rather than as a pass/fail verdict: the model learns which formulations are numerically fragile on FP16 hardware without the device becoming the oracle. If you later want the NPU to gate, the vendor precedent says to gate on a *two-reference ratio* — AWS Neuron's "is this error from Neuron, or just from BF16?" framing, or CANN Bench's `ErrorCount_NPU / max(ErrorCount_CPU, 1) ≤ 2` — which requires adding a same-precision CPU FP16 run you do not currently produce. That is the one genuinely missing piece of infrastructure in the whole design.

## Conclusion

The sharpest finding is that your two campaigns already contain an answer the headline numbers hide. The same 480 saved tensors support pass counts from 27/40 to 40/40, and the mutation evidence narrows the defensible range to a single order of magnitude: one FP16 epsilon (39/40, all generic corruptions caught) is justified, while KernelBench's 1e-2 (40/40, blind to a 0.1% bias) is not. Within that range, Option 4's magnitude-scaled bound dominates Option 3 on Run A at the cost of per-op modeling work; Option 3 captures most of the benefit in one line of code. Either way, the number that changes is a property of the harness, and the capability claim it licenses stays the same: gpt-6-astra builds correct OpenVINO graphs for these 40 tasks at near-saturation, and the physical NPU disagreements were never evidence of mistranslation.

The deeper implication is that this benchmark currently measures two things at once and credits both to the model. On-device accuracy varied by up to 5× the one-epsilon bound between runs because the model happened to pick different mathematically equivalent formulations, with no feedback and no selection pressure — so the "NPU-verified" rate is partly a lottery over graph lowerings. Closing that loop is the change that would turn this from a translation benchmark into a numerics benchmark, and it is worth doing in that order: validate the verdict against mutations, diversify the inputs, add a same-precision CPU reference, and only then let the hardware vote on acceptance.
